Pipeline Run Flow

What happens from the admin clicking "generate" to a saved draft: HTTP/SSE layer, orchestrator loop, sub-agents, and how each agent's context stays separate. Read from backend/src.

1. Layers in one picture

  • HTTP + SSE (routes/adminRuns.js, services/runRegistry.js): starting a run and watching a run are two different requests. The run lives in the server, not in the connection.
  • runPipeline (services/pipeline.js): owns the run, the shared state, and the emit function that feeds SSE.
  • Orchestrator: one long query() of the Agent SDK. The SDK runs its turn loop (model turn, tool call, tool result, model turn …). It only has two tools: spawn_researcher and spawn_writer.
  • pipeline MCP tool (services/orchestrator/tools.js): an in-process MCP server. Its handler is where a sub-agent is spawned and awaited.
  • Sub-agents: researcher (WebSearch, WebFetch) and writer (no tools). Each is its own query() with its own conversation.

3. The orchestrator loop (what the SDK does for you)

Your description, "when the agent finishes it sends the result back to main and it loops", is right in effect, but our code does not send that request. The loop is inside the SDK:

  1. SDK calls the Claude API with the orchestrator's message list. The reply ends with stop_reason: "tool_use" and a tool_use block (spawn_researcher).
  2. SDK invokes our MCP handler handleSpawn and waits for its promise. Nothing else is sent to the model meanwhile.
  3. The handler runs the whole sub-agent (minutes, many sub-agent turns) and returns a small JSON digest.
  4. SDK wraps the digest as the tool_result block matching that tool_use id, appends it as the next user message, and calls the API again.
  5. The orchestrator reads the digest and either calls another tool (go to 1) or replies with plain text and stop_reason: "end_turn". The query() then ends with a result message.

The sub-agent's own stop_reason checks (tool_use to keep going, end_turn to finish) happen in the sub-agent's own SDK loop. We only see the end of it: runAgentQuery resolves with the final result message, or throws an AgentError (max turns, budget, rate limit, ...).

How data moves between them

  • Researcher output goes into state.research (recordResearch), not into the orchestrator's chat.
  • The writer's input is built by combinedNotes(state) and mergedSources(state). The spawn_writer tool takes no arguments, so nothing the orchestrator model writes can reach the writer.
  • Writer output goes into state.draftMd. After the orchestrator ends, runPipeline reads state.draftMd to save the blog, not the orchestrator's last message.
  • The orchestrator receives only researchDigest / writerDigest: counts, booleans, remaining spawns, remaining budget, and an error code from a fixed allowlist (DIGEST_ERROR_CODES), so free text from the web or from errors cannot inject instructions.

5. Why the orchestrator request cannot arrive in the wrong order

The API rule: an assistant message containing tool_use must be followed immediately by a user message with a matching tool_result for every tool_use id. Breaking it gives a 400. Here is why that can't happen in this design:

  1. We never build the orchestrator's messages. The SDK appends the assistant turn and the tool_result itself. Our handler only returns a value. There is no code path where the server sends "the agent finished" text into the orchestrator's chat.
  2. The sub-agent run is inside the tool call. handleSpawn awaits runSub, so the orchestrator's tool_use stays open and no further request is sent until the handler returns. Sub-agent streaming goes to SSE, not to the orchestrator.
  3. Every branch of the handler returns a result. Bad input, LIMIT_REACHED, BUDGET_EXHAUSTED, SPAWN_IN_PROGRESS, sub-agent failure (failSub), timeout (AGENT_TIMEOUT), abort (ABORTED) and internal error (INTERNAL_ERROR) all return result() or errorResult(), so each tool_use gets its tool_result. Failures are reported as isError results, not thrown into the SDK.
  4. The handler cannot hang forever. Each spawn gets AbortSignal.timeout (researcher 300 s, writer 180 s), combined with the run signal and the MCP call's own signal via AbortSignal.any. The MCP server's timeout is RUN_TIMEOUT_MS + 60 s, longer than any of those, so the SDK never gives up on the tool call before our own limits fire.
  5. The busy lock handles parallel tool calls. If the model emits two tool_use blocks in one turn, the second sees state.busy and gets an error result SPAWN_IN_PROGRESS. It is still a valid, paired tool_result. checkSpawn and busy = true have no await between them, so there is no race. finally always clears busy.
  6. Sub-agents are physically separate sessions. Each runAgentQuery starts a new query() with persistSession: false, its own temp cwd, and an allowlisted env. They can't append to the orchestrator's history. Even the tool lists differ: orchestrator has only the two MCP tools, writer has none.
  7. SSE is one-way. emit writes into the registry buffer, which only feeds subscribers. Nothing in the browser path can write back into an agent's context.
  8. Event order on SSE is kept too. createThrottledEmitter batches text deltas (100 ms / 1 KB) but flushes before any non-delta event, and the handler calls flush() around orchestrator_action, agent_started and agent_completed. The registry then assigns the increasing id.
Where the guarantee actually comes from: the tool call is a synchronous-looking boundary. The orchestrator is suspended at tool_use until our promise resolves, and the SDK, not our code, writes the tool_result. I did not read the SDK's own source; this is the documented tool-use contract and matches how the code is written.
